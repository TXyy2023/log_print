# 排查常见问题

先确认当前工作目录、配置文件、实例状态路径三者对应，再检查插件状态。以下管理命令都要使用出问题实例的 `--state`。

## 启动提示状态文件已存在

先运行 `status` 判断原实例是否仍在运行。需要关闭时正常 `stop`，不要直接删除状态文件，也不要停止其他实例。连接失败时检查该路径的启动日志及相关进程，确认是否为遗留状态后再处理。

## 极短程序在启动时就退出

当前版本中，源程序过快结束可能与启动就绪检查交错，出现启动失败。程序采集教程让教学源停留 1 秒后退出以便完成握手；这不是对所有瞬时命令的可靠接入保证。遇到此问题保留 stderr 日志和源退出信息，区分源程序自身失败与启动时序问题。

## 读取结果为空

依次检查：

1. `streams` 中是否存在正确的流名；插件 ID 与流名不是同一概念。
2. 文件输入默认从启动时末尾开始，测试日志是否在启动之后追加。
3. 路径是否按启动工作目录解析到预期文件。
4. 程序输出是否仍在源程序自身的缓冲里。
5. 是否需要 `--wait-ms 1000` 等待新的记录。

使用 `status` 检查插件报告。后台插件 stdout 不一定出现在当前终端，启动结果会给出 stdout/stderr 日志路径。

## 读取重复、缺口或身份错误

重复读取默认从 1 开始，不会记住上一次读到哪里。按返回的 `next` 和 `epoch` 继续读取。

Gap 意味着请求位置已不可用，常见原因是未保存的旧数据被缓冲覆盖。增大缓冲不会找回已丢失历史。epoch 不匹配时确认是否创建了新的 Core 历史，不能直接丢弃身份校验并声称续读完整。

## 归档提示目标已存在

`mode: create` 用于新目标。继续旧归档时保留所有伴随文件，按 [恢复与完整性](guides/recovery.md) 使用 `resume`。不要只改 `append`：`output-file` 没有将它作为恢复开关。

## 改了配置却没有生效

`config set` 只修改当前进程支持的动态字段；编辑磁盘 JSON 不会自动重载。静态配置需要正常重启实例加载。各插件可修改字段见插件参考。

## 关停超时或归档失败

超时表示结果未知，进程可能仍在收尾。检查归档 `status.get`、进程及错误日志，保留目标和状态，不立即重启另一个写入者。

保存容量、写入权限或同步错误需要先处理实际原因。队列为空不能证明完整，需比较源最终 head 和归档共同 next，并确认没有 Gap 或错误。

## 提供问题信息

报告版本、操作系统、执行命令、脱敏配置、错误信息，以及源类型和能否复现。不要公开状态文件中的令牌，也不要默认附上含业务敏感内容的日志。
